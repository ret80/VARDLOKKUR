# Задача: Поддержка нескольких запущенных игр одновременно в Debug Server

## Проблема

Текущая архитектура Debug Server поддерживает **строго одну** игру:
- При подключении второй игры первая принудительно отключается (`debug-server.cjs:228-233`)
- Состояние хранится в одной переменной `let gameState = null`
- Нет механизма идентификации игровых сессий
- Debug Panel не может переключаться между играми

Это мешает:
- Тестировать мультиплеер с несколькими локальными экземплярами
- Отлаживать несколько карт одновременно
- Держать открытыми несколько сессий игры

## Текущая архитектура

### Файлы
| Файл | Описание |
|------|----------|
| `debug-server.cjs` | Основной Node.js сервер (прокси/ретранслятор), порт 3100, 338 строк |
| `src/game/debug/debug-server.ts` | Альтернативный TS-сервер с REST API, 587 строк (не используется в рантайме) |
| `src/game/debug/debug-api.ts` | API сбора и манипуляции состоянием ECS, 679 строк |
| `public/game-client.js` | Браузерный клиент, внедряемый в игру, 224 строки |
| `src/components/DebugPanel.tsx` | React-панель, подключается как "panel client", 717 строк |
| `tasks/debug-server-plan.md` | Исходный дизайн-документ |

### Текущий поток данных
```
[Game Tab]  ws://localhost:3100?role=game  →  Debug Server (port 3100)  →  [Panel Tab]
                                                                                   ↓
                                                                              React UI
```

- Игра пушит состояние каждые 100мс (10 FPS)
- Panel получает состояние через broadcast
- Panel отправляет команды (телепорт, спавн и т.д.) → сервер ретранслирует игре
- Лог-буфер: кольцевой буфер 10МБ, 50К записей

### Ключевые ограничения (barriers)

1. **Одна переменная gameState** — `debug-server.cjs:25` — `let gameState = null`
2. **Одна переменная gameClient** — `debug-server.cjs:25` — `let gameClient = null`
3. **Автозамена клиента** — `debug-server.cjs:228-233` — старый клиент убивается при новом подключении
4. **Нет ID в URL подключения** — `game-client.js:17` — `?role=game` но без instance ID
5. **Нет селектора в панели** — `DebugPanel.tsx` — нет UI для выбора между играми
6. **Broadcast без фильтрации** — состояние отправляется всем панелям без учёта сессии
7. **Команды без таргетинга** — команды отправляются единственному gameClient

## Предложение по решению

### 1. Идентификация сессий

**Вариант A: Автоматический UUID (Recommended)**
- При подключении game-client генерирует UUID (или использует `crypto.randomUUID()`)
- Передаёт в URL: `ws://localhost:3100?role=game&id=<uuid>`
- Сервер принимает ID, создаёт/обновляет запись в Map
- Если клиент не прислал ID — сервер назначает автоматически

**Вариант B: Ручной номер сессии**
- Пользователь вводит номер сессии в консоль браузера перед запуском
- Меньше удобства, но больше контроля

**Выбор: Вариант A** — автоматический UUID, без вмешательства пользователя.

### 2. Структура данных на сервере

```javascript
// Было:
let gameState = null;
let gameClient = null;

// Стало:
const sessions = new Map(); // id → { ws, gameState, connectedAt, label? }
```

### 3. Изменения протокола WebSocket

#### Подключение game-client
```
// Было:
ws://localhost:3100?role=game

// Стало:
ws://localhost:3100?role=game&id=<uuid>
```

#### Сообщение состояния (game → server)
```javascript
// Было:
{ type: 'state', data: { player, enemies, ... } }

// Стало (обратно совместимо):
{ type: 'state', data: { player, enemies, ... }, sessionId: '<uuid>' }
```

#### Сообщение состояния (server → panel)
```javascript
// Было:
{ type: 'state', data: { player, enemies, ... } }

// Стало:
{ type: 'state', sessionId: '<uuid>', data: { player, enemies, ... }, sessionLabel: 'Map 1' }
```

#### Команды (panel → server → game)
```javascript
// Было:
{ type: 'teleport', x: 100, y: 200 }

// Стало (обратно совместимо):
{ type: 'teleport', sessionId: '<uuid>', x: 100, y: 200 }
```

### 4. REST API — новые эндпоинты

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/debug/sessions` | Список всех активных сессий |
| GET | `/debug/sessions/:id/state` | Состояние конкретной сессии |
| GET | `/debug/sessions/:id/logs` | Логи конкретной сессии |
| POST | `/debug/sessions/:id/teleport` | Телепорт в конкретной сессии |
| POST | `/debug/sessions/:id/spawn-enemy` | Спавн врага в конкретной сессии |
| DELETE | `/debug/sessions/:id` | Закрытие сессии |

### 5. Debug Panel — новый UI

- **Дропдаун/табы** в верхней панели для выбора сессии
- При переключении — фильтрация состояния и команд по `sessionId`
- В списке сессий: ID, метка (если задана), статус (online/offline), кол-во врагов, HP игрока
- Кнопка "Обновить список сессий"

## План реализации

### Этап 1: Серверная часть (debug-server.cjs)

#### 1.1. Рефакторинг хранения состояния сессий
- Заменить `let gameState` и `let gameClient` на `Map<sessionId, sessionData>`
- sessionData = `{ ws, gameState, connectedAt, label }`
- Методы: `getSession(id)`, `setSession(id, data)`, `removeSession(id)`, `getAllSessions()`

#### 1.2. Обработка подключения с ID
- Извлечь `id` из query-параметра URL
- Если ID не передан — сгенерировать `crypto.randomUUID()`
- Заменить логику автозамены (строки 228-233) на обновление существующей сессии
- Отправить клиенту подтверждение подключения с ID

#### 1.3. Обновление обработки сообщений state
- Извлечь `sessionId` из сообщения (или использовать ID из подключения)
- Сохранять состояние в `sessions.get(sessionId).gameState`
- Broadcast панелям с полем `sessionId`

#### 1.4. Обновление обработки команд
- Извлечь `sessionId` из команды (или использовать текущую сессию панели)
- Ретранслировать команду только в нужную gameClient WS
- Возвращать ответ с ID сессии

#### 1.5. REST API для списка сессий
- Добавить обработчик `GET /debug/sessions`
- Возвращать массив `{ id, connectedAt, gameState: { player: { hp, x, y }, enemyCount, ... } }`
- Добавить `GET /debug/sessions/:id/state`
- Добавить `DELETE /debug/sessions/:id`

### Этап 2: Клиентская часть (public/game-client.js)

#### 2.1. Генерация и отправка ID
- При инициализации проверить `localStorage` на наличие `debugSessionId`
- Если нет — сгенерировать `crypto.randomUUID()` и сохранить в `localStorage`
- Передать ID в URL: `?role=game&id=<id>`
- Отправлять ID в каждом сообщении состояния

#### 2.2. Обработка подтверждения от сервера
- При успешном подключении получить ID от сервера
- Вывести ID в консоль для отладки: `[DEBUG] Session ID: xxx-xxx-xxx`

### Этап 3: Debug Panel (src/components/DebugPanel.tsx)

#### 3.1. Список сессий
- При подключении загрузить список сессий через `GET /debug/sessions`
- Отображать дропдаун/табы с названиями сессий
- Автообновление списка каждые 5 секунд

#### 3.2. Фильтрация по сессии
- Все данные состояния фильтровать по выбранному `sessionId`
- Все команды отправлять с полем `sessionId`
- При отсутствии выбранной сессии — показывать "No session selected"

#### 3.3. Визуальное отображение
- Цветовая индикация: зелёный = online, красный = offline
- Краткая сводка: HP игрока, кол-во врагов, позиция
- Кнопка "Disconnect" для каждой сессии

### Этап 4: Обратная совместимость и тестирование

#### 4.1. Graceful degradation
- Если клиент не отправляет ID — сервер назначает автоматически
- Если панель не отправляет ID — сервер ретранслирует команду всем играм (fallback)
- Существующие клиенты без ID продолжают работать

#### 4.2. Тестирование
- Запустить 2+ экземпляра игры
- Убедиться, что состояния не смешиваются
- Проверить переключение в Debug Panel
- Проверить REST API `/debug/sessions`
- Проверить, что отключение одной игры не влияет на другие

## Риски и нюансы

1. **Лог-буфер** — текущий `logBuffer` общий для всех сессий. Нужно решить: общие логи или раздельные?
   - **Решение**: Оставить общие логи (все игры пишут в один буфер), но добавить фильтр по `sessionId` в REST API

2. **Дубликат `game-client.js`** — файл дублируется в корне проекта и в `public/`. Актуальный — в `public/`. Корневой удалить.

3. **Port 3100** — если запускается несколько инстансов Vite, порт может конфликтовать.
   - **Решение**: Не проблема — debug server один на все игры, игры подключаются к нему через WebSocket

4. **Производительность** — при N играх broadcast увеличивается в N раз.
   - **Решение**: При 3-5 играх не критично. Если нужно — добавить lazy broadcast

5. **Обратная совместимость** — старые клиенты без ID должны продолжать работать.
   - **Решение**: Fallback на автоматический ID
