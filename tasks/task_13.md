Отличная задача. Текущая реализация `MapRenderSystem` действительно представляет собой обычный класс, который вызывается императивно при загрузке карты, что нарушает принципы ECS. Кроме того, в `RenderQueue` отсутствует отсечение невидимых объектов (Viewport Culling), что приводит к лишней нагрузке на GPU.

Ниже представлен подробный план рефакторинга для приведения архитектуры к полноценной ECS-модели с единым конвейером рендеринга.

---

### 🛠 План рефакторинга рендеринга карты и очереди отрисовки

#### Этап 1: Создание компонента `Map` и сущности карты в ECS
В ECS вся информация о мире должна храниться в компонентах.
1. **Добавить компонент `Map`** в `src/game/ecs/ecs-components.ts`.
   * Он должен хранить параметры текущей карты (размеры, ID подземелья) и ссылки на созданные `GraphicsHandle` (батчи для земли, стен и домов).
   ```typescript
   // src/game/ecs/ecs-components.ts
   export const MapState = defineComponent({
     groundHandle: 'int32',
     wallsHandle: 'int32',
     housesHandle: 'int32',
     width: 'int32',
     height: 'int32',
     dungeonId: 'int32',
   });
   ```
2. **Создание сущности карты.**
   * При загрузке карты (`src/game/ecs/ecs-map-loader.ts`) вместо прямого вызова генерации геометрии, система должна создавать (или обновлять) **синглтон-сущность** с компонентом `MapState`.
   * Процедурная генерация батчей (`drawTileBatch`, `drawWallGeometry` и т.д.) происходит **один раз** в момент создания этой сущности. Хэндлы сохраняются в компонент.

#### Этап 2: Превращение `MapRenderSystem` в ECS-систему
Система должна работать в общем цикле `tick` или `render`, а не вызываться вручную.
1. **Рефакторинг в систему.**
   * Переименовать `MapRenderSystem` в функцию `mapRenderSystem(world: World)` (или класс, реализующий интерфейс ECS-системы).
   * В каждом кадре система делает запрос `query(world, [MapState])`.
2. **Регистрация в RenderQueue.**
   * Система находит сущность карты и использует `RenderQueue.upsert()` для добавления её графических батчей в очередь.
   * Поскольку карта статична, система не создает новые `Graphics`, а лишь убеждается, что ссылки на них актуальны и лежат в очереди с правильным `layer` (например, `RENDER_LAYER.GROUND` для земли и `RENDER_LAYER.DYNAMIC` для стен).
   * Если сущность `MapState` уничтожается (переход на другую локацию), система удаляет старые хэндлы из `RenderQueue` и уничтожает их через `IRenderer`.

#### Этап 3: Интеграция `RenderSystem` (Динамические объекты)
`RenderSystem` (которая обрабатывает игрока, врагов, дропы) уже частично работает с `RenderQueue` через `ensureRenderEntry`.
* Убедиться, что `RenderSystem` и новая `mapRenderSystem` работают параллельно и независимо, просто наполняя общий `RenderQueue` своими `RenderEntry`.
* Динамические объекты должны иметь актуальные координаты `x`, `y`, которые считываются из компонента `Position`.

#### Этап 4: Доработка `RenderQueue` (Viewport Culling и IRenderer)
Текущий `flush(renderer)` только сортирует объекты и обновляет их свойства. Нужно добавить умное отсечение.
1. **Передача параметров камеры.**
   * Метод `flush(renderer, viewport)` должен принимать параметры области видимости: `{ camX, camY, viewW, viewH }`.
2. **Логика отсечения (Culling).**
   * Во время итерации по `entries` `RenderQueue` вычисляет bounding box объекта.
   * Если объект гарантированно находится за пределами `viewport` (например, `x + width < camX` или `x > camX + viewW`), `RenderQueue` пропускает вызовы методов `IRenderer` для этого объекта (или ставит `visible = false`).
   * *Особое внимание:* Батчи карты (ground, walls) имеют размер всей карты, поэтому они всегда будут "видимы" с точки зрения их bounding box, но динамические объекты (враги, дропы) будут эффективно отсеиваться.
3. **Финальный рендеринг через IRenderer.**
   * После сортировки по `(layer, y)` и проверки видимости, `RenderQueue` применяет итоговые трансформации (`setGraphicsPosition`, `setGraphicsAlpha`, `setGraphicsZIndex`) только для видимых объектов.

### 💡 Архитектурный результат (Data Flow)
1. **Map Loader** создает сущность `Map` с хэндлами батчей.
2. **MapRenderSystem** (ECS) находит `Map` и регистрирует статичные тайлы/стены в `RenderQueue`.
3. **RenderSystem** (ECS) находит динамические сущности (Position + Sprite) и регистрирует их в `RenderQueue`.
4. **RenderPipeline** завершает кадр, вызывая `RenderQueue.flush()`.
5. **RenderQueue** сортирует всё по Z-индексу, отсекает то, что за экраном, и батчит вызовы к **IRenderer**.
6. **IRenderer** отрисовывает финальную сцену.

Такой подход полностью соответствует принципу **Data-Oriented Design** и делает рендеринг карты неотъемлемой частью ECS-цикла, а не внешним "костылем".
